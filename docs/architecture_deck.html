Overview

Three sections, one schema

This is the map for the rest of the talk, one band per section. Top, classification: notes land in NOTE_RAW, a dynamic table rolls them up per encounter incrementally with no LLM, a stream captures what's new, and a task wakes every minute but only runs when the stream has data. One set-based AI_COMPLETE classifies the batch, always with the champion config. The gap queue on the right is fed by production output and drafts the next taxonomy. Everything here is in one schema.

1 · Classification

Ask for the leaf, derive the rest, give it an honest way out

Mismatch is structurally zero

The model picks only the subtheme. Theme and category come from a join to the taxonomy, so a theme/subtheme mismatch can't happen. It's not a metric to watch anymore.

Hierarchy in the prompt, leaf in the answer

The prompt still carries the full [CATEGORY] Theme > Subtheme: description hierarchy and routing rules, so close calls like post-op vs general follow-up stay decidable.

The escape hatch is the gap detector

A small model under a strict enum rarely picks NO_GOOD_MATCH on its own, so it's paired with LOW confidence. Both were 100% precise on genuine gaps.

Evidence on every label

A free-text evidence field rides along. It's what makes human review of flagged rows quick.

Two common ways to set this up are a hierarchical prompt, where the model sees the full category, theme and subtheme structure, and a subtheme-only answer, where theme and category are looked up. This does both: the model sees the whole hierarchy in the prompt but only answers with the leaf. The example labels here are illustrative. On NO_GOOD_MATCH: the rubric wording mattered a lot. Telling the model not to use it for poor fits made it force a match; describing it as an expected, useful outcome got it to flag real gaps without false positives elsewhere.

2 · Taxonomy governance · creating v1

An LLM drafts v1 of the taxonomy

PROPOSE_TAXONOMY() turns a design sample into a complete draft tree in one structured call. It writes a DRAFT and never touches what the pipeline is using.

-- what comes back, one call
{ "rationale": "...",
  "nodes": [ {
    "category":     "...",
    "theme":        "...",
    "subtheme":     "...",
    "description":  "...",
    "routing_note": "..." } ] }

The gap is planted, and checked

The design sample leaves out transportation notes, and notes that hint at it. One note mentioning it in passing was enough for the generator to pick it up.

Output is checked on the way in

Raw output lands in a temp table first, so a failed call is inspectable. Duplicate subtheme names are dropped before insert.

One large taxonomy prompt, with the result landing as rows in a versioned table. The prompt has four parts: structure, quality, coverage, and an explicit anti-anchoring instruction. The model choice is a parameter; v001 in this build came from openai-gpt-5.2 over 163 sample notes. It came back with 23 themes against a 15 to 20 target, and one node with a blank subtheme name, which we named Administrative Matter Only by hand. Models don't always follow every rule, so generation drops blank nodes on insert, a person reviews and locks the draft, and LOCK_TAXONOMY refuses blank or duplicate labels as a backstop. The planted gap: design samples rarely cover everything, so here the miss is explicit (transportation barriers) to give gap detection something real to find later.

2 · Taxonomy governance · storage

How a taxonomy version is stored

Two tables hold every version. Two views turn a version into what the model sees. Everything downstream carries the version_id it was produced under.

TAXONOMY_NODE, a few real rows (v002 is a fork of v001)

v002Clinical Symptoms And Red FlagsGastrointestinal SymptomsNausea Without Vomiting
v002Clinical Symptoms And Red FlagsGastrointestinal SymptomsVomiting Episodes

A new version is new rows

A locked version's rows never change. FORK_TAXONOMY copies them under a new id and sets parent_version_id, so comparing two versions is one query:

SELECT category, theme, subtheme FROM TAXONOMY_NODE
 WHERE version_id = 'v002'
EXCEPT ... WHERE version_id = 'v001'
This is what a version physically is. Two tables: TAXONOMY_VERSION has one row per version with its status, its parent, and who generated, locked and reviewed it. TAXONOMY_NODE has one row per subtheme, with the theme and category carried as columns, so there's no tree to walk. The prompt text and the enum aren't stored anywhere: TAXONOMY_RENDERED computes both from the rows, for any version. That's why a draft can be evaluated with exactly the same machinery production uses. TAXONOMY_ACTIVE is the same view filtered to the approved version. Everything downstream carries a version_id: a config pins one, every label is stamped with the one it was produced under, and gold labels are per version. A fork is a copy of the rows with a new id and a parent pointer, so diffing two versions is plain SQL.

2 · Taxonomy governance · lifecycle

The lifecycle of a taxonomy version

Every step from first draft to production is a procedure call. A version can only be edited as a DRAFT, and only reaches production when a config bound to it is promoted past the eval gate.

Only the champion's version ships

APPROVED is set only by PROMOTE_CONFIG, past the eval gate. Drafts and locked candidates render too (TAXONOMY_RENDERED) so they can be scored, but never reach production output.

Guardrails live in the procedures

Only a DRAFT can be edited or locked. Lock refuses blank, reserved or duplicate labels. Exactly one version is ever APPROVED, and registry tables are CREATE IF NOT EXISTS.

Gold labels are version-specific

The first evaluation on a new version labels its gold set, and re-labeling is refused after that, so every eval of a version uses the same answer key.

This is the life of one version. It starts as a DRAFT, either drafted by a model or forked from an existing version, and a person edits it node by node. Locking freezes it: that's the point where it can be gold-labeled and evaluated, because an evaluation of something that can still change isn't evidence. It reaches production only when a config bound to it is promoted past the gate, which is covered in the next section. Promotion marks the previous approved version SUPERSEDED, and it stays available as a rollback target. A draft that doesn't make it can be rejected, and it stays in the table as a record. Revisions re-enter at the start, as a new DRAFT built from the gap encounters. The procedures enforce the rules at every step: no edits after lock, no blank or duplicate labels, and never two approved versions.

2 · Taxonomy governance · revising

Classification gaps become the signal for the next version

The classifier's own uncertainty is the input to revision: encounters it can't place point to concepts the taxonomy is missing.

Why two signals

A small model under a strict enum rarely picks NO_GOOD_MATCH. LOW confidence is the higher-recall half. Both were 100% precise on genuine gaps.

Precision beats recall here

You don't need every instance of a missing concept, just enough clean examples to name it. Five was enough.

Add-only keeps history comparable

No renames or re-parenting, so existing labels and gold stay valid, and the reviewer reads one added row instead of 79.

This is how production feeds governance. Two signals come straight off the champion's output: NO_GOOD_MATCH, where the model says nothing fits, and LOW confidence, where it forced a fit and told us so. Evaluation runs of candidates never show up here, so the queue is about real traffic. The gap queue shows the note text and the model's evidence, so a reviewer can name the missing concept without trusting the model's conclusion. Then a model drafts the smallest add-only revision that covers the evidence, and it's allowed to say there's no real gap. The draft is a starting point: edit it, lock it, and it goes through evaluation like any other candidate. Gap detection needs volume: with only the 200 gold encounters classified, one gets flagged; across all 1,000 it's five.

2 · Taxonomy governance · revision loop

The revision loop, and every step is a SQL object

This is the prompt and taxonomy update cycle, shaped like an ML model registry. Production runs the champion. Its drift is checked by evaluating it against its own previous score. Production output surfaces the gaps, a model drafts an add-only revision, and a person edits and locks it. Then it's bound into a candidate config with the same prompt, registered, and evaluated on gold against the champion: that pass labels gold for the new version on first use. If the gate passes, a person promotes it; if not, they fix it or promote with a reason that gets logged. Two human decision points, both explicit. A prompt change takes the same path from step 6, and costs less because it reuses the champion's gold labels.

Evaluation that catches what an average hides

There's no hand-labeled gold set for this domain yet, so the build shows how to bootstrap one: a frontier model from a different family than the classifier labels each gold encounter one at a time with the full taxonomy. It's still model grading model, and I say that out loud. HUMAN_VERIFIED is a real column and RUN_EVAL has a verified-only switch, which refuses today because nobody has adjudicated yet. The run-level metrics on the right need no gold at all, so they can be watched on every production batch. 3 · Evaluation and operations · gate and alert

The gate decides what ships. The alert watches for regressions.

EVAL_GATE is a view: every evaluation gets PASS or the first reason it failed, judged against the champion in production. Promotion reads it; the alert watches the champion with it.

Why check 4 exists: in comparable prior work, a variant cleared the overall floor at 0.914 while terse inputs quietly fell from 1.00 to 0.80. An aggregate-only gate would have shipped it.

The gate is a view, so it's always current and anyone can query it. It reads one config row: a 0.70 accuracy floor, a 1% error ceiling, a 0.10 allowed drop per segment, and a minimum of 20 encounters before a segment is gated, because at n=10 one note is 10 points. Checks run in order and the first failure is the reason you see. The fourth check is the one that earns its place: it compares every category, label-count and note-length segment to the champion's latest evaluation. Nobody pins a baseline by hand, so the comparison can't quietly drift away from what's actually in production. It isn't vacuous: tighten the margin to 0.02 and the revision fails on the Clinical Symptoms category, which dipped 2 encounters. For an eval of the champion itself, the baseline is its own previous eval, which is the drift check. The alert is the operational half: once a day, if an eval of the champion didn't pass, it fires. A failing candidate isn't an incident, refusing to promote it is the gate doing its job. It's created suspended because delivering it needs an email notification integration and verified recipients; both come from the alert's CONFIG, so wiring it up is an ALTER, not a code change.

3 · Evaluation and operations · promotion

Register, evaluate, promote: the only way into production

The same loop as an ML model registry. A config is the unit: prompt + model + taxonomy version. Candidates are scored on gold before they can replace the champion, and production never runs anything else.

Measured on this build, 200 gold encounters

Prompt-only candidate

Same taxonomy, stricter second-label rule. 0.840 vs champion 0.830, PASS. Reused the champion's gold labels: one gold run, about 1.07 credits.

Taxonomy candidate (hand-edited v002)

Champion prompt on a fork of v001 that adds transportation. 0.885 vs 0.830, PASS. Unplaceable gold 9 → 1, Access category 0.750 → 0.889.

Rolling back

Promoting v001 again failed on that same Access regression. It went through only with a written reason, which is now in PROMOTION_LOG.

This is the ML-registry flow. The unit isn't the taxonomy or the prompt on its own, it's the config: prompt, model and taxonomy version together, because that's what actually produces a label. Register a candidate by forking the champion. EVALUATE_CONFIG classifies the gold set with exactly that recipe as an evaluation run, so nothing reaches the business output, and if the taxonomy is new it labels the gold set for it first. The gate compares it to the champion. If it passes, a person promotes it, and that's one transaction: the taxonomy is approved, the old one superseded, the config becomes the champion, and the log row records the verdict it was judged on. If it fails, promotion is refused unless someone writes down why they're shipping it anyway. The numbers on the right are from this build. Note the rollback: going back to v001 is itself gated, and it failed on exactly the category the revision fixed, which is the gate telling the truth.

No chunking to tune

One set-based statement per batch. Cortex parallelizes internally, so there's no batch size or worker count to tune. The full 1,000 took ~52s in the September run.

The rubric beats the model

On a comparable task, writing the decision policy down was worth +45 to 49 accuracy points. Switching models at equal information was worth about 1. That's why a smaller model is the right default here.

Cost monitoring is a view. Every classification run writes a PIPELINE_RUN row carrying its query id, because a procedure can't set its own query tag, and RUN_COST joins that to CORTEX_AISQL_USAGE_HISTORY. That's real, measured consumption per run, including output tokens. AI_COUNT_TOKENS returned NULL for every model we tried in this account, so usage history is the better source anyway. The interesting part: input dominates about 30 to 1, because the rubric and enum go out on every call. So taxonomy size is the cost lever, not model choice. When the taxonomy regenerated from 55 to 78 subthemes, cost went from 3.67 to about 5.4 credits per thousand. Nothing regressed, it just got richer.

Demo app

A thin UI over governed objects

Six pages in the order the work happens, each naming the SQL objects it reads. All behavior lives in Snowflake. The only write path is an allowlist of the same procedures you'd call by hand, so the app can't skip the gate.

No INSERT, UPDATE or DELETE anywhere in the app. Runs locally against your Snowflake account; it's scaffolded from the Snowflake App Runtime template, so it can deploy as an APPLICATION SERVICE without a rewrite. Not deployed yet.

The pitch here is "a thin UI over governed Snowflake objects", so the app deliberately shows its sources on every page. The pages follow the lifecycle: author a taxonomy, author a prompt, evaluate and promote, run production, then monitor and revise, which loops back to page 2. Two rules the code enforces: no SQL in components, and all writes go through one endpoint that only calls allowlisted procedures. So the app can't promote without the gate, can't run a candidate in production, and an override reason it collects lands in the same PROMOTION_LOG a SQL user would write to. When a guardrail fires, like locking a draft with a blank label or scoring a partial run, the app shows it as information instead of crashing. If we deploy it, we'd want caller's rights on the read paths so it respects each user's grants.

Appendix · Design decision

Why the LLM step is a task, not a dynamic table

Every label is stamped with the config (prompt + model + taxonomy) that produced it. Where you split the pipeline decides who chooses to spend money on re-classification.

The deterministic rollup still gets the full declarative treatment. Only the step that costs money per row is split out. Triggered tasks don't fire on dynamic-table streams, so the task is scheduled every minute and gated by WHEN SYSTEM$STREAM_HAS_DATA.

Backup slide, in case the question comes up. It's tempting to make the whole thing dynamic tables. But if classification is a DT joined to the champion config, promoting a new one silently re-bills everything. Splitting at the stream turns that into an explicit, costed decision. And because backlog is defined as "no production label from the champion", a promotion automatically means the whole corpus is due, with no special code path. Until you run it, the business keeps seeing the previous labels.
